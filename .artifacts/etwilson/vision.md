# Vision: Yet Another Recipe App (YARA)

> A low-friction meal-planning app that kills the nightly "what's for dinner?" decision and hands you a ready-to-shop grocery list.

---

## Problem Statement

Cooking dinner regularly fails not because cooking is hard, but because the *decisions around it* are exhausting. Every evening starts with "what do I make tonight?" — a recurring, draining choice that pushes people toward eating out. Grocery planning compounds the problem: ingredients get bought for a single meal, partially used, and thrown away. The cumulative friction makes home cooking feel like more effort than it's worth, even for people who enjoy and are good at cooking.

YARA exists to automate the mundane parts of home cooking — the deciding, the list-making, the planning — so the only thing left is the part that's actually enjoyable: making the food. It's for people who can cook but don't want to *think* about it every single day.

---

## Product Positioning

YARA is a personal meal-planning tool for capable home cooks who want to eliminate decision fatigue and grocery waste. Unlike recipe databases (which give you more choices, not fewer) or full lifestyle apps (which demand accounts, onboarding, and engagement), YARA is deliberately minimal: maintain a small library of recipes you actually make, generate a multi-day plan in seconds, and walk out of the store with exactly what you need. It is local-first and account-optional — usable immediately with zero signup, with an optional account only when you want persistence across devices or to share a list with someone else.

---

## Users & Personas

- **The primary cook (owner-operator).** A capable home cook in a busy household who enjoys cooking but is worn down by the daily decision and planning overhead. Wants to plan a few days at a time, shop efficiently, and stop wasting food and money on takeout. Values speed and low friction above all — every extra tap or required field is a reason to abandon the app.
- **The shared-list recipient (e.g. a partner).** Doesn't necessarily use the app to plan, but needs to *see* the shopping list — typically on their own phone, at the store. Should be able to view a shared list with no account and no setup.
- **The account-averse visitor.** Anyone who wants to try the app without being forced to sign up. Should get a fully functional experience backed by local storage, with the option to create an account later without losing their data.

---

## Core Features

- Personal recipe library — a small, curated set of recipes the user actually cooks (each with ingredients, quantities, and steps).
- Low-friction recipe import — add recipes by URL or by pasting raw recipe text (including text generated by an LLM like Claude or ChatGPT), parsed into structured form.
- Multi-day meal planning — assign recipes across N days quickly, with minimal interaction.
- Auto-generated shopping list — consolidated across all planned meals so quantities are summed per ingredient (no duplicate line items).
- Share-by-link — generate an "anyone with the link can view" read-only link for a shopping list (and reusable for recipes/plans via the same mechanism).
- Local-first persistence — full core functionality with no account, backed by client-side storage.
- Optional accounts with server sync — sign up to persist data across devices and browsers; local data migrates up to the server on account creation.
- Ownership-based access — each user owns their own recipes, plans, and lists; no cross-user visibility except via explicit share links.

---

## Explicit Non-Goals

- **No forced authentication.** The core flow must never require an account to use.
- **No social/community features.** No feeds, following, friend systems, comments, ratings of other people's content, or recipe discovery marketplace.
- **No per-user permission grants in v1.** Sharing is "anyone with the link can view" only — no per-recipient access control, no edit-sharing, no collaborative editing.
- **No nutrition tracking, calorie counting, or diet/macro management.**
- **No native mobile apps in v1.** Web only. (API should be designed so mobile *could* be added later — see Tech Stack — but no mobile client is built.)
- **No pantry/inventory tracking in v1.** ("What can I make with what I have" is explicitly deferred.)
- **No grocery-delivery or store integrations** (no Instacart, no price lookups, no in-store ordering).
- **No large public recipe database.** The library is the user's own curated set, not a searchable catalog of thousands of recipes.

---

## Product Constraints

- **Account-optional by design** — anonymous users get full core functionality via client-side persistence; this is a hard product requirement, not a nice-to-have.
- **Low friction is the governing principle** — any feature that adds a required step to the core plan-and-shop flow must justify itself against abandonment risk.
- **Server-backed persistence is in scope** — local-only storage is wiped on cache clear or browser switch, so a real server-side DB is required for accounts and sharing.
- **No special compliance burden** — no sensitive/regulated data (no health, payment, or PII beyond basic account identity). Share links carry non-sensitive content (recipes, grocery lists).
- **Single-developer personal project** — scale expectations are low; no high-availability or enterprise uptime requirements. Deployment target should be low-cost or free.

---

## Tech Stack

- **Frontend:** Svelte, built with Vite. Tailwind CSS for styling, with a solid component library (shadcn-style / DaisyUI-family preferred). Responsive layout.
- **Backend:** Rust web server (chosen deliberately for the developer to gain Rust web-server experience; deviate only with compelling reason).
- **API:** Decoupled from the frontend so a mobile client could be added later without a backend rewrite. GraphQL is acceptable and a reasonable fit given likely future mobile support; REST is the fallback. API style is a known unknown to be resolved early.
- **Persistence:** Client-side storage for local-first / anonymous use (localStorage vs IndexedDB to be decided during implementation), plus a server-backed database for accounts, sync, and sharing.
- **Local dev:** Docker Compose.
- **Deployment:** A free or low-cost host (specific target TBD).

## Milestones & Phasing

### v1 — The Core Loop
- Personal recipe library (create, view, edit, delete own recipes).
- Recipe import via URL and/or pasted text, parsed into structured recipes.
- Multi-day meal planning (assign recipes to N days quickly).
- Auto-generated, ingredient-consolidated shopping list.
- Share-by-link (read-only) for shopping lists.
- Local-first persistence with no account required.
- Optional account with server sync; local data pushes up to the server on account creation.
- Ownership-based authorization (own-only access; sharing only via link).

### v2 — Reduce Friction Further
- "What can I make tonight?" mode — surface recipes makeable with what's on hand.
- Pantry / staples tracking — exclude items the user always has from shopping lists.
- Plan-level conveniences — suggestions, randomization, or quick re-use of prior plans.
- Possible mobile client (enabled by the decoupled API from v1).

---

## Success Criteria

- **v1:** The developer can import a handful of their real recipes (by URL or paste), generate a meal plan for N days in under a minute, get a single consolidated shopping list with summed quantities, and share that list with their wife via a link — all without being forced to create an account to use the core flow. Creating an account migrates existing local data to the server.
- **v2:** The developer can get a usable "what should I cook" answer without manually planning — either from a "what can I make tonight?" prompt or a suggestion/randomizer — and shopping lists automatically exclude pantry staples the user already owns.

---

## Open Questions

- **Recipe import parsing approach.** The *requirement* (low-friction URL + paste import) is firm, but the *implementation* is unresolved. Options include deterministic parsing of schema.org `Recipe` JSON-LD for URLs, heuristic/structured parsing of pasted text, or an LLM-assisted parse for messy input. Reliability, cost, and complexity trade-offs need evaluation early, since import friction is make-or-break for the product.
- **API style (GraphQL vs REST).** GraphQL is a reasonable fit given probable future mobile support, but prior experience suggests it can be overkill. Decide early, as it shapes the backend architecture.
- **Client-side storage mechanism.** localStorage vs IndexedDB for local-first persistence — to be decided based on data shape and size during implementation.
- **Deployment target.** Specific free/low-cost host not yet chosen; affects how the Rust backend and database are provisioned.
